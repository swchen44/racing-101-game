# 台北來源模型賽道設計草案

日期：2026-10-20。狀態：使用者已確認設計並授權自主實作，目前於 `feat/taipei-source` 整合驗收。此文件保留設計要求，實際完成範圍以[台北驗收紀錄](../../TAIPEI-ACCEPTANCE.md)為準。

## 1. 目標與範圍

以 `/Users/swchen.tw/git/rea_study_gta_taipei` 的來源模型與生成模組，新增一條具有台北生活街景特色的封閉賽道。保留來源造型與色彩，藉由構圖、材質恢復、場景密度與照明提升成品品質。保留現有四條賽道與車庫。

本階段只交付台北。後續預留香港、高雄、東京、倫敦、臺中；使用者正在下載素材，實作順序尚未決定。本階段不替其他城市補下載整包、建場景或產生空白城市選項。

已確認的三輪決策見[訪談紀錄](../../research/2026-10-20-city-decisions.md)。其餘技術選擇為本草案提出的工程方案，受來源與代表路段驗證結果約束。

## 2. 玩家體驗

- 賽道選單新增台北主題賽道。維持中文／英文、三種時段、現有競速與追捕規則，以及桌機／手機橫向操作。
- 路線為具有城市特色的虛構閉環，不宣稱真實道路與地標位置一比一還原。保持現有平面賽道合約，首版無可行駛立體交叉或坡道物理。
- 玩家可選來源 `sedan`、`taxi`、`sports`、`suv`。追捕與警車使用來源 `police`；贓車與 GP 對手從可用來源四輪車挑選。原有四條賽道的八車選擇保留。
- 幽靈車延續現有行為，使用玩家當前選擇的來源車透明顯示已錄軌跡；紀錄另保存錄製車款與路線版本供相容性判斷，不假稱透明車必然是錄製當時的車型。追捕過場角色採來源人物，所需動作須驗證骨架及動作轉接。
- 機車、公車等先停靠路側；行人於人行空間活動。初版車道內僅保留玩家、賽事對手與警車，不新增隨機一般車流、闖入車道的行人或開放城市任務。
- 追車、遠景、車頭及駕駛艙相機保留。駕駛艙可見內裝須來自來源；未定位的內裝列為缺件，不能沿用舊 3D 內裝冒充。既有 HUD 與操作提示屬保留的介面系統。

## 3. 美術方向與路線節奏

先完成白天版本，檢查模型、招牌、玻璃、比例及接縫，再完成黃昏與夜晚。使用暖白店光、琥珀街燈、灰水泥與青綠鐵皮，保留來源風格；夜景亮度與 bloom 不能掩飾缺材質。

| 分段 | 視覺及駕駛節奏 | 已定位的來源候選 |
|---|---|---|
| 街屋起跑 | 連續店面建立城市尺度，起跑直線視野清楚 | `guling-book-street`、`bolero-1934`、來源小黃與機車 |
| 夜市外緣 | 街景密度提高，車道從市場外緣通過，前方彎道保持可見 | `linjiang-market`、來源攤位與街屋構件 |
| 廟埕開闊彎 | 空間放開，寺廟成為彎道外側的主景，樹與前場留白 | `cisheng-temple` |
| 商業街回程 | 零售立面與少量遠景高樓，回到適合加速的直線 | `donqi-ximen`、`regent-hotel`、`breezy-center` |

原型分屬不同地點，按主題組合；不把同一整排夜市複製成所有街廓。道路沿用現有寬度與碰撞合約作起點，先調沿街配置，只有實際駕駛證據要求時才變動幾何合約。每個分段保留主景、輔景及視線留白。

## 4. 來源與資產邊界

新賽道可見建築、地面、道路表面、路緣、標線、護欄、植栽、號誌、道具、車體、輪胎、人物、警燈與過場模型均須可追溯至來源。允許拆分、組裝、比例與材質調整，保留修改紀錄。相機、燈光控制、HUD、物理與賽事程式沿用本遊戲。

來源稽核也涵蓋警車動態路障、起終點／檢查點顯示、車庫預覽圓盤與背景幾何，以及帶有可見幾何／貼圖的 Boost 噴焰、煙、光池與胎痕。沿用特效觸發及後製控制不表示可以直接沿用其中的舊模型或視覺資產。這些構件同樣需來源轉接；若缺必要來源，列入缺件處理，不能只稽核靜態街景便宣稱全來源。無資產的曝光、bloom、色彩與光源控制屬保留的渲染系統。

每件交付資產記錄：穩定 asset ID、原 module／symbol 或 Blender 檔、原檔 SHA-256、生成參數／seed、轉換版本、衍生關係、幾何與材質統計、尺寸／方向、檔案摘要及已知缺口。新的場景顯示物件也保留 asset ID，供驗收檢查來源覆蓋。

本地 170 個 Blender 檔包含 67 外觀、60 室內、27 人物、13 車輛、2 號誌頭、1 動畫庫；不是完整可用城市包。已知缺少 Canvas 圖集、部分材質效果、完整街道配套及車輪分件。需回來源生成器補齊。找不到來源的必要構件列為缺件，不由現有 `city.js` 或舊車模自動補上。

來源資料維持唯讀；抽取、轉換與試驗使用獨立輸出目錄，不覆寫既有 Blender 檔與 receipt。已有 README 記載再利用授權未確認；保留該來源狀態。本設計範圍為本機研究與開發，不包含素材對外發布。

## 5. 建議的接入方式

採「來源生成器恢復材質／零件結構 → 可追溯資產 → GLB 與必要材質轉接 → 本遊戲城市配置」。現有 Blender 模型可作幾何與比例參考，但不能靠直接另存 GLB 補回遺失的招牌、玻璃與輪組。

來源 Three.js r186 與本遊戲 r160 分離：抽取工具可維持來源版本，遊戲先維持 r160，以標準資產及數值資料傳遞；不直接混用兩版物件圖或載入來源整套應用程式。特殊 shader 與 Canvas 圖集須逐件測試烘焙或材質轉接效果。這是優先驗證的路線，尚未證明任意來源效果皆可保真。

建議模組責任如下，實際檔名可在實作計畫細化：

| 模組 | 責任與界線 |
|---|---|
| 城市配置 | 每城指定來源清單、賽道路徑、街區擺放、時段參數、可用車款與顯示名稱 |
| 資產載入與資源管理 | 按城市載入、快取、實例化、來源標記、失敗狀態及釋放 |
| 場景組裝 | 將來源道路與街景配置到賽道；維持可見道路與不可見碰撞軌跡一致 |
| 車輛與角色轉接 | 提供現有物理／AI 可使用的車身、輪組、燈號、骨架與動作 |
| 來源抽取工具 | 在開發時還原來源資料、烘焙、輸出與驗證；不隨遊戲啟動 |

新賽道配置與舊賽道的程序化顯示路徑分離；新場景不呼叫舊場景建造器作為缺件 fallback。城市選單只列出已有可用內容的城市。

## 6. 需要處理的現有整合點

- **載入狀態**：現有 `startRace()`、車庫預覽與 builder 同步建立物件。城市與車款資產須先載入，再讓同一批已驗證資產進入選單預覽與開賽流程。載入中提供進度／狀態；失敗可重試或返回選單，不能默默顯示舊模型。一場賽事固定選擇快照，只允許最新有效請求提交；世界、車與模式角色全就緒後才一次切換。快速切換、重複開始、返回或錯序完成不得產生混合場景；取消／失敗釋放暫存資源，原場景保持可用。車庫預覽採相同規則。
- **車輪合約**：`Car._syncMesh()` 依賴 `bodyGroup`、`wheels[].spinner`、`wheels[].group` 與轉向標記；目前來源車的一體 mesh 不能直接滿足。須從來源車模生成器保存輪組、pivot、車頭方向與燈號節點。
- **車型尺度與手感**：每車提供與來源尺寸一致的輪徑、軸向、碰撞尺寸及 cockpit／hood／mirror 相機錨點，並明列既有 tune、選單 stats 與模型的對應。移除來源車路徑對固定輪徑的假設。沿用既有物理系統，校準數值而非另造一套物理；翻車 pivot、路障碰撞與逮捕落腳點一併驗證。
- **模式覆蓋**：`opponents.js`、`police.js`、`chase.js`、`ghost.js`、`carpreview.js` 與逮捕過場都有自己的模型建立路徑。只改玩家車會讓舊模型混入，所有路徑都要透過城市限定的來源車／人物選擇。
- **道路與看板**：保留 `Track.query()` 及檢查點資料；來源道路顯示層需沿相同軌跡組裝。來源看板構件承載既有看板功能；未找到來源構件時列缺件，不能生成舊自製看板。
- **資源釋放與狀態隔離**：現有 `disposeObject()` 會直接釋放 geometry/material，只有部分 texture 支援 shared 標記。新 GLB 實例若共用資源，需要明確擁有者與最後使用者釋放機制，並避免舊清理路徑提前銷毀共用資源。警燈、幽靈透明度、時段及角色動畫會修改狀態，因此可變 material／skeleton 按實例隔離，不能全部共用。離開選單、切換城市或取消下載時，過期載入結果不得覆蓋新選擇，也須釋放其資源持有權。不得只補 texture 標記便認定處理完成。
  Immutable geometry／texture 可共享，material state、skeleton、AnimationMixer 與燈號控制器按實例擁有；自訂 shader 行為須有明確複製策略，不假定 material.clone() 自動保留。釋放包含 ImageBitmap 與動畫綁定，驗證預覽、玩家、AI、幽靈及路邊人物互不污染。
- **存檔與設定**：新 track ID／source vehicle ID 獨立，舊成績與幽靈紀錄保留。切換城市時將不適用車款改成該城市的有效選項；不將舊車紀錄錯配為新模型。新城市幽靈紀錄包含 schema、route revision 與錄製車款；路線改版後不播放不相容軌跡，保留舊紀錄而非誤套。單純材質改版不必使路線紀錄失效。
- **PWA**：資產按城市載入及快取，核心遊戲更新不要求一次 precache 所有未來城市。現有 `sw.js` 的 activate 會刪除當前兩個 cache 以外的所有 cache，須改為有界的命名空間與版本淘汰規則，保留仍相容的城市資產。每城以 manifest 版本建立候選 cache，確認所有必要資產完整後才標示離線可用；中斷時保留未就緒狀態並可重試。核心與城市 manifest 不相容時要求取得相容版本，不能混用。需測試缺檔、更新與容量不足，不能顯示離線可用後才在賽中發現缺件。
  manifest 使用版本固定的資產 URL／hash，避免同源 network-first 混搭新舊版本。離線清單涵蓋 loader、必要 decoder、貼圖與字型。瀏覽器清除或淘汰快取後重新判斷可用性，不沿用過期的 ready 標記。

## 7. 分階段交付邊界

下列為設計驗證階段；逐檔工作與測試指令將在完整設計確認後另寫實作計畫。

1. **來源外觀樣本**：帶字店面、玻璃建築、道路／號誌、可轉向車輪的車、具骨架人物。比較來源參考、轉換結果及 r160 顯示，明列差異。
2. **台北白天代表路段**：約 30 秒正常駕駛，包含入彎、主景與出彎。先確認來源覆蓋、尺度、視線、輪組及材質；它是品質檢查點，不代替完整賽道交付。
3. **完整台北閉環**：四段街景、來源車庫、現有四種模式與追捕雙角色、幽靈車、重啟／結算／換場景。
4. **三時段與裝置驗收**：完成黃昏／夜晚，分畫質調整遠景；雙美術評審、桌機效能、手機實機與離線檢查。未通過項目保持未完成。

## 8. 統一美術評分與證據

採獨立審查文件的八項準則作為共同 rubric，取代研究階段各自不同的候選表。每項 0–10，加權總分亦為 0–10：

| 準則 | 權重 |
|---|---:|
| 城市辨識與構圖 | 20% |
| 賽道與動態目標可讀性 | 20% |
| 光照、曝光與材質完整性 | 15% |
| 模組比例與接縫品質 | 10% |
| 街區變化與重複控制 | 10% |
| 車輛、人物與演出 | 10% |
| 桌機／手機與 HUD 相容性 | 10% |
| 效能限制下的畫面穩定性 | 5% |

設計者自評與獨立審查都須總分 ≥8.5；城市辨識與賽道可讀性各 ≥8，重大缺陷清零。所有必要項目須有證據；N/A 不能刪去重算、不能當成通過。兩位評審分歧保留理由，不以平均抵銷問題。

每城固定六個鏡位：起點、主要識別點、繁忙街段、急彎入口、開闊端景、近景細節。三時段共 18 張；另有完整跑圈、Boost 與追捕過場證據，以及桌機／手機有 HUD 的畫面。固定 commit、素材 hash、seed、相機、時段、解析度與品質設定，保存 before／after 和缺陷 ID。

其他城市完成前，台北先檢查至少三組非標題的地方線索；跨城市比較待其他城市有畫面後進行。研究中建議的五人匿名辨識測試是額外使用者研究，尚未列為本次承諾或代替已確認的雙美術審查。

## 9. 工程驗收與實測邊界

- **來源**：所有新場景可見模型有來源標記及資產紀錄；玩家／AI／警車／幽靈／過場／街道配套均覆蓋。必要模型缺件為阻擋項。
- **功能**：四模式及追捕雙角色可開賽、重啟與結算；車輪旋轉／轉向、攝影機、後視鏡、車庫預覽、來源人物動作、幽靈與小地圖正確；保留原四賽道的必要回歸檢查。
- **效能**：桌機目標 60 FPS、手機至少 30 FPS。每次附硬體、瀏覽器、解析度、pixelRatio／畫質、測試路段與時長；記錄 frame-time 分布、draw calls、triangles、載入 bytes/time、可用的資源統計。初期樣段用於制定幾何與材質預算，不先憑模型三角形數宣稱達標。
- **手機**：桌機改視窗尺寸只驗證排版，不能證明手機 FPS。若尚無可用手機實機測試，手機效能保持未驗證，不降低門檻或宣告完整完成。
- **生命週期**：反覆重啟、城市／舊賽道切換與預覽後檢查資源釋放、缺材質及持續增長；按所有權處理共用 geometry/material/texture。
- **離線與錯誤**：測試完整城市下載後離線重載、初次未下載時的提示、下載中斷與重試、快取版本更新；素材錯誤不得回填舊模型。

此段為規劃時的證據邊界；目前實作與驗證進度見[台北驗收紀錄](../../TAIPEI-ACCEPTANCE.md)。來源 Blender receipt 及研究者素材分數不能代替上述遊戲驗收。

## 10. 草案審查紀錄

環境美術代理確認三輪決策一致，沒有需要新增訪談的產品取捨。技術代理指出動態物件來源、城市 cache、可變實例狀態、幽靈版本、非同步切換、車型尺度六項漏點，已補入本稿。這是文件審查，不是實作或遊戲畫面驗收。
